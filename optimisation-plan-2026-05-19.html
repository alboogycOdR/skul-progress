2. What it means for the SKUL stack

Cross-referencing this device list with SKUL's current frontend state surfaces several priorities, grouped by urgency.

Critical Hurts users today

  1. Frontend is still on the Vite dev server in production. KNOWN_ISSUES.md ISSUE-005 tracks this as "deferred to Sprint Omega". Vite dev server ships unminified, unbundled JS with HMR overhead. On a Tecno POP with a Helio A22 and 2 GB RAM, this is the difference between a usable site and a frozen tab.
    Action: Multi-stage Docker build with npm run build + Nginx-served dist/. This is now an urgency upgrade, not "nice to have".
  2. Hero images on read-more pages weigh 130–185 KB each. Across /about, /how-it-works, /learning that's ~500 KB just for heroes. On Zambian mobile data (~$1.50/GB at MTN/Airtel), that costs the user money.
    Action: Add loading="lazy" to offscreen images; generate WebP/AVIF variants (50–70% smaller); use <picture> with fallbacks.
  3. KaTeX maths rendering. Currently loaded for every chat message. Non-maths students pay the cost.
    Action: Confirm code-split / lazy-load behaviour; if not split, do so.
  4. No initial JS bundle budget.
    Action: Set a target — aim for ≤ 100 KB gzipped to first paint. Enforce in CI.

High priority Mitigates older-OS reality

  1. Browser baseline. Set Vite's target to support Chrome 80+ / iOS Safari 14+. Avoid bleeding-edge ES2022+ syntax unless transpiled.
  2. PWA capabilities. Manifest is already in place (added in the 2026-05-19 frontend revamp pull). Next step: a proper service worker for offline page caching and shell-app behaviour. Material for users on flaky 2G/3G in rural areas.
  3. Touch targets and font sizes. Test at 360×640 (Tecno/itel resolution) and 412×915 (Samsung A-series). Touch targets < 44×44 px and body text < 14 px both fail accessibility on these screens.

Medium priority Quality of experience

  1. Reduce font weight variants. Currently loading Nunito at weights 400/600/700/800/900 + Nunito Sans at 300/400/500/600/700 — roughly 10 font files. Cull to 3–4 weights (e.g. 400, 600, 700, 800). Saves ~200 KB.
  2. Cap image dimensions in DOM via srcset. Hero images are 1376×768 source; rendered at ~360 px wide on phones. Serve a 720px variant for mobile via <picture> with srcset. ~70% saving on those screens.
  3. Skeleton loaders. Chat SSE streaming already does perceived-speed well. Extend the pattern to conversation lists, admin pages, etc.

Lower priority Polish

  1. Static pre-render the read-more pages (/about, /how-it-works, /learning). These are essentially static content. Pre-rendering eliminates JS overhead entirely for those routes.
  2. Data-saver mode. Detect Save-Data: on request header or navigator.connection.saveData flag; skip decorative imagery, lower image quality.

3. Suggested sprint sequencing

SprintDeliverableWhy this order
1 Multi-stage Dockerfile, frontend production build, Nginx-served dist/ (ISSUE-005) Single biggest perf win for budget devices. Unblocks everything else.
1 Bundle size baseline + CI budget enforcement Prevents regression as we iterate
2 Image optimisation pass (WebP/AVIF, srcset, lazy-load) High data-cost reduction
2 Font weight cull Cheap quick win
3 Service worker + offline page cache Real PWA capability on patchy networks
3 Device testing on Tecno POP / Samsung A12 (real hardware or BrowserStack) Validation rather than optimisation
4 KaTeX code-split + skeleton loaders Polish
4 Static pre-render of read-more pages Lower priority, smaller win

4. Validation approach

Before declaring any optimisation "done", validate on devices that match the target list:

  • Real hardware (preferred): Tecno POP 3 or Spark 4, Samsung Galaxy A12, Infinix Hot 10. Source from Lusaka if needed.
  • BrowserStack alternative: Covers most listed devices. Useful for quick smoke tests, less useful for actual performance feel.
  • Lighthouse mobile audit: Aim for Performance score ≥ 80 with the "Slow 4G + Moderate CPU throttle" preset on every PR.
Reality check: the goal isn't a perfect Lighthouse score on a high-end iPhone. It's "the site usable on a Tecno POP 3 over 3G in Ndola." Synthetic benchmarks are a proxy, not the goal.

5. Open questions / follow-up research

The source document was brief and explicitly offered to expand. Next research request worth making:

  1. Specific resolutions and viewport sizes of each top-10 device, with portrait + landscape coverage. The 360×640 / 412×915 baseline I'm working from is approximate.
  2. OS-version distribution in Zambia specifically (what fraction of users are still on Android 9 vs 12 vs 14? iOS 14 vs 17?).
  3. Network conditions — average effective bandwidth in major Zambian markets (Lusaka, Ndola, Kitwe, rural areas) on MTN, Airtel, Zamtel. Sets realistic perf budgets.
  4. Storage / RAM constraints — particularly relevant for service worker cache sizes and image preloading strategies.
